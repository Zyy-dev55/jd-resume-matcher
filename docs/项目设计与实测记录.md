# 项目设计与实测记录

> 这份文档记录「为什么这么设计」和「数字是怎么来的」，是对 `README.md` 的补充。README 讲怎么跑，这里讲取舍与局限，便于代码评审、面试追问，也便于后续维护者在没有原作者在场时理解上下文。

## 1. 项目定位

一个**面向求职场景的大模型应用工程实践**：输入一段岗位 JD，先从自己的项目经历库里检索可核对的证据片段，再让模型按固定 JSON 结构输出「匹配点 / 能力缺口 / 简历改写建议 / 适配分」。

它要解决的不是「模型能不能答」，而是**模型答得不可信怎么办**。因此整条管线的重心放在三件事上：证据可溯源、输出可校验、失败可降级。

技术选型上刻意保持**零第三方依赖**（只用 Python 标准库），目的是把 RAG、结构化输出、降级链、评测集这些环节全部自己实现一遍，能逐行讲清原理，而不是调框架的封装。

## 2. 数据流

```
JD 文本
  │
  ├─ ① 检索   retrieval.py：BM25 + 中文 2-gram，从 knowledge.py 的证据片段召回 Top-K
  │            设 MIN_EVIDENCE_SCORE = 5.0，低于阈值的片段不进生成上下文
  │
  ├─ ② 证据   每条片段带 chunk_id（如 P1-C1）与项目归属，生成时只能引用这些原文
  │
  ├─ ③ 生成   llm.py：OpenAI 兼容协议，固定 JSON Schema，temperature 0.1
  │            Key 只从环境变量或本地 config 读，不写进代码、不打印日志
  │
  ├─ ④ 校验   llm.py::_parse()：字段完整性 + evidence 逐条比对片段原文
  │            不是原文子串 → 剔除该匹配点，计入 dropped_invalid_evidence 并写入 gaps
  │
  ├─ ⑤ 降级   解析失败视为该服务商失败，按 providers 顺序换下一家；全挂返回纯检索结果
  │
  └─ ⑥ 评测   evaluate.py：25 条固定用例，报告落盘到 reports/
```

## 3. 关键取舍（以及为什么）

| 决策 | 理由 |
| --- | --- |
| 用 BM25 + 中文 2-gram，不用向量库 | 证据库只有 4 个项目、几十条短文本，且专有名词多（chunk_id、模型名、框架名）。BM25 零依赖、结果可解释、无需 embedding 服务。`search()` 按可替换接口设计，后续可接向量检索做 A/B。 |
| 证据阈值取 5.0 | 不是拍脑袋：负例 Top1 得分实测 1.96–3.22，正例普遍 12 以上，5.0 留出明显间隔。低于阈值返回「无可核对证据」，从源头减少硬凑匹配点。 |
| Prompt 之外再加一层解析校验 | 真实调用时 GLM 把**项目名**当证据原文填进 `evidence`（5 条里 3 条不合规），尽管 Prompt 明确要求引用原文。结论：幻觉抑制不能只靠提示词，必须有代码兜底。 |
| JSON 解析失败也算服务商失败 | 格式不对的输出若强行使用，后面的匹配结论就不可信；统一按失败处理，走降级链，行为可预期。 |
| 全挂时返回纯检索结果而非报错 | 这是求职工具的底线：不让模型故障阻塞用户，也不因为模型失败就编造结论。 |
| 默认 `k=4` 未改动 | 已定位到 Top4 会被 P1 片段占满、导致 P2 的 MySQL 片段进不了上下文。用 `-k 8` 验证过有效，但改默认 k 会让「Hit@4 100%」的口径变成 Hit@8，评测集与所有对外指标都要重做，因此在有完整回归之前保持原值。 |
| 不使用 LangChain / Dify / RAGFlow | 这些框架定位与适用场景已了解，但本项目要展示的是对底层环节的理解，故零依赖自实现。简历与 README 均如实标注「未使用上述框架」。 |

## 4. 指标口径与实测数据

分三层，**不要混用**：

| 层 | 来源 | 结果 | 说明 |
| --- | --- | --- | --- |
| 检索层（离线） | `python matcher.py --eval --offline` | 25 条（20 正例 + 5 负例）；正例 Hit@4 **100%**；负例正确拒绝率 **100%** | 不需要任何 Key，反映 BM25 + 阈值是否有效 |
| 模型层（真实调用） | `python matcher.py --eval`（智谱 GLM `glm-4-flash`，2026-11-12 22:46） | 25 条；JSON 遵守率 **100%**；平均延迟 **6747 ms**；降级率 **0%** | 明细见 `reports/eval_report.md` / `.json` |
| 接入链路（mock） | `python matcher.py --selftest --mock` | 5 / 5 通过 | 本机起 mock 端点，验证正常解析、500 切换、全失败降级、json_object 回退、日志不泄密；`reports/selftest_report.json` |

**重要时间点**：`reports/eval_report.md` 里那组真实模型数字，产生在「解析层证据引用校验」加入**之前**，属于基线。加入校验后新增了 `evidence_compliance`（证据引用合规率）字段，离线模式下为 `N/A`，需重新跑一次 API 模式才能覆盖基线。README 的模型对比表已标注这一点。

**只实测过智谱 GLM 一家**。`config.example.json` 里 Qwen / DeepSeek / OpenAI / 硅基流动属于接入配置（统一 OpenAI 兼容协议），未做过横向对比；Ollama 是本地免 Key 方案，`disabled: true`。对外材料一律写「已实测智谱 GLM，其余为接入配置」，不写「对比过多个模型」。

## 5. 已知局限（如实列出，不掩饰）

1. **检索召回偏置**：默认 Top4 常被 P1 占满，P2 的能力（如 MySQL）可能进不了上下文，导致模型把它列进 `gaps`。已用 `-k 8` 验证，尚未改默认，理由见第 3 节。
2. **证据库是手写事实清单**：`knowledge.py` 里的 4 个项目经历是静态文本，不是从代码库自动抽取，新增项目需手工添加片段。
3. **评测集规模小**：25 条，负例只覆盖 5 个无关领域，长尾边界表述未覆盖。
4. **单 Agent 判定闭环**：没有多 Agent 编排、没有工具调用的通用协议层，只有「工具 / 判定 / 记忆」的基础组件。
5. **只有命令行入口**：没有图形界面，没有打包成可执行文件，也不与「招聘信息筛选与投递助手」Chrome 扩展联动——后者只是证据库里被描述的一个项目，两者代码完全独立。
6. **模型侧未做成本统计**：延迟有实测，Token 成本未记录。

## 6. 文件职责

| 文件 | 职责 |
| --- | --- |
| `matcher.py` | CLI 入口，参数 `--demo` / `--eval` / `--jd` / `--jd-file` / `--selftest` / `--providers` / `--offline` / `-k` |
| `jd_matcher/knowledge.py` | 4 个项目经历 → 带 `chunk_id` 的证据片段，唯一事实来源 |
| `jd_matcher/retrieval.py` | BM25 + 中文 2-gram、证据阈值常量 |
| `jd_matcher/llm.py` | Provider / ProviderChain：OpenAI 兼容请求、结构化输出、解析层校验、逐家降级、Key 隔离 |
| `jd_matcher/evaluate.py` | 25 条用例执行、指标计算、`reports/eval_report.*` 生成 |
| `jd_matcher/selftest.py` | mock 端点 5 项链路自检 |
| `eval_set.json` | 25 条评测用例（20 正例标 `expect_project`，5 负例标 `NONE`） |
| `config.example.json` | 默认服务商配置，所有 `api_key` 为空；缺少 `config.json` 时自动读它 |
| `接入大模型指南.md` | Key 获取渠道、PowerShell / cmd / Git Bash 三种语法、本地 Ollama 方案、安全提醒 |
| `run_all.bat` + `sample_jd_negative.txt` | Windows 离线一键演示（三条命令均带 `--offline`，不调用模型） |
| `reports/` | 评测与自检报告，作为实测证据保留 |

## 7. 复现命令

```bash
python matcher.py --providers          # 查看服务商状态（不打印 Key）
python matcher.py --selftest --mock    # 无需 Key，5 项链路自检
python matcher.py --demo --offline     # 无需 Key，看检索证据
python matcher.py --eval --offline     # 无需 Key，25 条检索层评测
python matcher.py --demo -k 8 --offline   # 验证 Top4 偏置问题
```

接真实模型（PowerShell 示例，三种 shell 语法不通用）：

```powershell
$env:ZHIPU_API_KEY = "完整Key"
python matcher.py --demo       # 注意：不要加 --offline
python matcher.py --eval       # 25 次请求，免费模型注意限流
```

## 8. 安全约定

- `config.json`、`reports/last_match.json`、`.env`、`__pycache__/` 已在 `.gitignore` 中，**不进版本库**。
- 任何文件都不含真实 API Key；`selftest.py` 里的 `selftest-placeholder` 是自检用的假占位符。
- Key 只从环境变量读，调用日志与 `--providers` 输出都不含密钥内容。
